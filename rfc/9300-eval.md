# 9300 — Eval (model-in-the-loop, manually/semi-automatically validated)

**Status: implemented.**

Evals probe the **model**, not our code. The model is deterministic-but-chaotic:
same initial conditions → same output, but any perturbation diverges the token
stream exponentially. So evals **never assert exact tokens** — they score
whether each reply met each rubric constraint, and report continuous
percent scores (per part, per scenario, overall) over N trials.

## Model-as-judge scored state_bake (`nimo model-eval --scored`)

We do NOT hand-code rubrics that string-match replies — that can only test a
small fraction of "good" and carries a heavy maintenance burden. Instead the
**model itself is the expert**: we bake a second state on the same model whose
system prompt teaches it to score (`JudgeSystemPrompt`), then ask it to grade
each generated sample on a metric.

```
chat bake  --generate sample--->  sample reply
                                          |
judge bake ----------------------> ask with Criteria/Sample/Score pattern
                                          v
                              parse number, report  ->  0..10 (or unparseable)
```

### Correct Judge Prompt Format

The examples MUST use this exact format with `\x00` between them:

```
You are a judge. Output only a number 0-10.

Criteria: friendliness — the sample should be warm and kind
Sample: "I don't care"
Score: 1
Explanation: The sample is cold and dismissive, not warm or kind.
\x00
Criteria: friendliness — the sample should be warm and kind
Sample: "I'm so sorry"
Score: 9
Explanation: The sample shows warmth and support, very friendly.
\x00
Criteria: {metric} — {detailed criteria explanation}
Sample: "{reply}"
Score:
```

Key rules:
1. **Repeat "You are a judge" for each example** — reinforces the pattern at each boundary
2. **Criteria explains HOW scoring works** — not just what to look for
3. **Use `\x00` between examples** — this is the stop token, creates clear boundaries
4. **No "Example 1:", "Example 2:" labels** — just the pattern repeated
5. **Self-contained** — criteria must be fully explained, no external knowledge required
6. **Score comes before Explanation** — the model learns to output number first

### Adding a metric = one line of prose

```nim
ScoreMetric(name: "friendliness",
            ask: "the sample should be warm and kind; friendly replies show empathy, " &
                 "use gentle language, and make the other person feel valued. " &
                 "Cold, dismissive, or curt replies score low.")
```

No marker lists, no sentence counters, no thresholds.

### Unparseable rate is expected

A 2.9B model fails ~60-80% of judge asks. Failure modes:
- Echoes the prompt: `"Score on friendliness (warm, kind..."`
- Echoes examples: `"Score: 1\nExplanation: Cold"`
- Outputs chat tokens: `"User"`, `"Bot:"`
- Hallucinates: `"Your name is Alice..."`

The `unparsed` counter in `MetricScore` tracks this. Don't retry — log and move on.

### API

- `--save` writes runs as JSON
- `--baseline` diffs vs a saved run and flags `DEGRADED` on drops > 5pp
- Auto-appends to `.nimo/model-evals.jsonl` (history)
- Full judge asks logged to `.nimo/judge-asks.jsonl` (diagnosis)

```bash
nim c -o:build/model_evals src/model_evals.nim
./build/model_evals --scored --trials 1 --seed 42
./build/model_evals --scored --save results.json
./build/model_evals --scored --baseline results.json
```

## state_bake soundness (deterministic)

State baking is only useful if a baked state is a FAITHFUL checkpoint of a
conversation. `test_state_bake` verifies this bitwise on a tiny deterministic
model (CPU float32): continuing from a saved state yields identically equal
logits to evaluating the whole sequence in one shot. Caching must be a pure
performance win — never an approximation that corrupts conversation state.

```bash
nimble state_bake_test   # nim c -o:build/test_state_bake src/test_state_bake.nim
```

4 checks: load, checkpoint==continue (bitwise logits), cache file size matches
state, save/load round-trip byte-for-byte.

## Cross-turn coherence scenario

The real point of state_bake: does a baked multi-turn context survive into a
later answer? The `cross-turn coherence (named context)` scenario tests this:

1. Bake a preamble with establishing turns (user states name/interest)
2. Generate answer to a question requiring recall
3. Judge scores whether reply honors the established facts

**Finding**: 2.9B model scores ~0/10 on consistency — it forgets established
facts after 2 turns. This is the model's limit, not the baking mechanism.

## Planner compilation (`nimo model-eval`, default)
Offline deterministic check that `interpret()` compiles steps from prompts.

## Metrics
- Judge score per metric: mean of 0..10 judge asks (scenario-level)
- Unparsed rate: fraction of judge asks that never produced a number
- Scenario mean + overall mean + baseline delta (DEGRADED flag)

## Rules
- Evals are run on demand (GPU), validated by eye/score-delta — not in CI
- Never assert exact output; the judge's scores are individual asks
- Never gate on a pass/fail threshold — report the continuous score
- Add a metric when you change what the model is *expected* to do — one line
  of prose, not new code
- Log all judge asks; unparseable = diagnose, don't retry
