# 9300 — Eval (model-in-the-loop, manually/semi-automatically validated)

**Status: implemented.**

Evals probe the **model**, not our code. The model is deterministic-but-chaotic:
same initial conditions → same output, but any perturbation diverges the token
stream exponentially. So evals **never assert exact tokens** — they score
whether each reply met each rubric constraint, and report continuous
percent scores (per part, per scenario, overall) over N trials.

## Model-as-judge scored state_bake (`nimo model-eval --scored`)

We do NOT hand-code rubrics that string-match replies — that can only test a
small fraction of "good" and carries a heavy maintenance burden. Instead the
**model itself is the expert**: we bake a second state on the same model whose
system prompt teaches it to score (`JudgeSystemPrompt`, few-shotted with
format examples), then ask it to grade each generated sample on a metric.

```
chat bake  --generate sample--->  sample reply
                                          |
judge bake ----------------------> ask "Score on <metric>: 0-10" (repeat)
                                          v
                              parse number, average  ->  0..10
```

Maintenance to add a metric = **one line of prose** (name + what to look for),
not marker lists, not sentence counters, not thresholds.

- Each scenario generates a sample with the chat bake, then asks the judge to
  score it on each metric (`askJudge`). The judge is chaotic too, so we ASK
  REPEATEDLY and average — a small model occasionally omits the number, so we
  re-ask up to 4x and report `unparsed` when it still doesn't.
- Scores are continuous `0..10` (scenario + metric + overall), never pass/fail
  — a threshold hides 90->70 drift a mean exposes.
- `--save` writes runs as JSON; `--baseline` diffs vs a saved run and flags
  `DEGRADED`; every run auto-appends to `.nimo/model-evals.jsonl` (history).

Newsflash (RTX 2050, seed 42, trials-1): a 2.9B model is a *weak, noisy*
judge — ~40% of asks return no number even after retries, and its grades are
harsh/erratic (a "hard day" sample scored friendliness-unparseable, and the
overall median was lopsided). Model-as-judge works mechanically; the judge's
signal quality is the open question and depends on a stronger model (or a
judge trained for rubric grading).

```nul
nimo model-eval --scored --trials 2 --seed 42
nimo model-eval --scored --save results.json
nimo model-eval --scored --baseline results.json
```


`--save <file>` writes the run as JSON; `--baseline <file>` diffs against a
saved run and flags `DEGRADED` on any part or overall dropping > 5pp.

```bash
nim c -o:build/model_evals src/model_evals.nim
./build/model_evals --scored --seed 42
./build/model_evals --scored --seed 42 --save results.json
```

## state_bake soundness (deterministic)

State baking is only useful if a baked state is a FAITHFUL checkpoint of a
conversation. `test_state_bake` verifies this bitwise on a tiny deterministic
model (CPU float32): continuing from a saved state yields identically equal
logits to evaluating the whole sequence in one shot. Caching must be a pure
performance win — never an approximation that corrupts conversation state.

```bash
nimble state_bake_test   # nim c -o:build/test_state_bake src/test_state_bake.nim
```

4 checks: load, checkpoint==continue (bitwise logits), cache file size matches
state, save/load round-trip byte-for-byte.

## Bake examples (manual eval)

The system prompt baked into state carries `User: hi / Bot: Hello!` style
examples. The `bake-examples teach turn format` scored scenario confirms the
model answers AS the bot (no `User:` echo, non-empty reply) — i.e. the baked
examples actually teach the chat turn format. Verified by rate on the real
model; the rubric itself is deterministic code.

## Planner compilation (`nimo model-eval`, default)
Offline deterministic check that `interpret()` compiles steps from prompts.

## Metrics
- Judge score per metric: mean of repeated 0..10 judge asks (scenario-level).
- Unparsed rate: fraction of judge asks that never produced a number (judge
  signal-quality self-diagnosis).
- Scenario mean + overall mean + baseline delta (DEGRADED flag).

## Rules
- Evals are run on demand (GPU), validated by eye/score-delta — not in CI.
- Never assert exact output; the judge's scores are averaged over repeated asks.
- Never gate on a pass/fail threshold — report the continuous score so drift is
  visible.
- Add a metric when you change what the model is *expected* to do — one line
  of prose, not new code.
