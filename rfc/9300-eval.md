# 9300 — Eval (model-in-the-loop, manually/semi-automatically validated)

**Status: implemented.**

Evals probe the **model**, not our code. The model is deterministic-but-chaotic:
same initial conditions → same output, but any perturbation diverges the token
stream exponentially. So evals **never assert exact tokens** — they score
whether the reply landed inside a rubric's **basin of attraction**, and report a
pass rate over N trials.

## Scored state_bake (`nimo model-eval --scored`)

Bake (system instructions + user message) → generate → score against a rubric →
pass rate over N trials. The scorer (`scoreReply`) is deterministic code
(unit-tested in L0); the model is its chaotic input.

```bash
nim c -o:build/model_evals src/model_evals.nim
./build/model_evals --scored --seed 42
```

Current run (real model, RTX 2050, seed 42):
```
  tool-call on write request: 0.0 (0/5)   <- model never emits [tool] run_pipeline!
  meeting intro anchors:      1.0 (5/5)
scored state_bake: 50% (5/10)
```

The 0/5 tool-call rate is a **real signal**: the harness's
`user -> [tool] -> dispatch -> write` path depends on the model emitting a
marker it doesn't reliably produce. Evals exist to surface this; tests can't.

## Planner compilation (`nimo model-eval`, default)
Offline deterministic check that `interpret()` compiles steps from prompts.

## Metrics
- Tool-call accuracy: did the reply contain a well-formed tool call?
- Multi-turn consistency: 3+ turns, no context loss (rubric on remembered facts)
- Attractor rate: fraction of trials scoring ≥ threshold (default 0.7)

## Rules
- Evals are run on demand (GPU), validated by eye/rate — not in CI.
- Never assert exact output; always score + rate over ≥3 trials.
- Add an eval when you change what the model is *expected* to do.
