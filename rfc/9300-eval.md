# 9300 — Eval (model-in-the-loop, manually/semi-automatically validated)

**Status: implemented.**

Evals probe the **model**, not our code. The model is deterministic-but-chaotic:
same initial conditions → same output, but any perturbation diverges the token
stream exponentially. So evals **never assert exact tokens** — they score
whether each reply met each rubric constraint, and report continuous
percent scores (per part, per scenario, overall) over N trials.

## Scored state_bake (`nimo model-eval --scored`)

Bake (system instructions + user message) → generate → score against a rubric →
scores over N trials. The scorer (`scoreReply`) is deterministic code
(unit-tested in L0); the model is its chaotic input.

Scores are **continuous** (percentage / x-out-of-y per scenario and overall),
never pass/fail — a threshold hides 90->70 drift that a mean exposes. Each
scenario also reports a **per-part breakdown** where every rubric constraint
gets a rate and an explanation of what was actually observed in the replies
(e.g. "no [tool] call parsed — reply: 'Roses, the flowers…'"). An eval not
only says *where and why*, but explains exactly which rubric part failed.

Rubric primitives support **qualitative** — non-classically-testable — traits:
- `required` / `forbidden`: exact wording constraints
- `anyOf`: at least one of a family of markers (a tone/sensory proxy, so we
  don't over-fit any single word)
- `minSentences` / `maxSentences`: pacing/concision proxies (sentence beats)
- `minLen` / `maxLen`: substance / overlong-looping
- `expectToolCall`: tool-call emission

`--save <file>` writes the run as JSON; `--baseline <file>` diffs against a
saved run and flags `DEGRADED` on any part or overall dropping > 5pp.

```bash
nim c -o:build/model_evals src/model_evals.nim
./build/model_evals --scored --seed 42
./build/model_evals --scored --seed 42 --save results.json
./build/model_evals --scored --baseline results.json
```

Current run (real model, RTX 2050, seed 7):

```
  friendly tone on a hard day:        100.0%  (warm-marker + no putdown)
  followed a length instruction:      100.0%  (concision <= 2 sentences)
  engaging prose has pacing:           50.0%  — often truncates to 2 beats
  vivid description engages senses:    66.7%  — some replies under 2 beats
  overall: 79.2%
```

The pacing/vivid numbers expose a real artifact: with `maxTokens=50` the model
can't reliably sustain 3 sentence-beats in prose before truncation (often
drops into the turn-form break instead). These are the non-classically-testable
qualities — friendliness, instruction-abidance, prose pacing — which is exactly
what a rubric eval, not a unit test, is for.

## state_bake soundness (deterministic)

State baking is only useful if a baked state is a FAITHFUL checkpoint of a
conversation. `test_state_bake` verifies this bitwise on a tiny deterministic
model (CPU float32): continuing from a saved state yields identically equal
logits to evaluating the whole sequence in one shot. Caching must be a pure
performance win — never an approximation that corrupts conversation state.

```bash
nimble state_bake_test   # nim c -o:build/test_state_bake src/test_state_bake.nim
```

4 checks: load, checkpoint==continue (bitwise logits), cache file size matches
state, save/load round-trip byte-for-byte.

## Bake examples (manual eval)

The system prompt baked into state carries `User: hi / Bot: Hello!` style
examples. The `bake-examples teach turn format` scored scenario confirms the
model answers AS the bot (no `User:` echo, non-empty reply) — i.e. the baked
examples actually teach the chat turn format. Verified by rate on the real
model; the rubric itself is deterministic code.

## Planner compilation (`nimo model-eval`, default)
Offline deterministic check that `interpret()` compiles steps from prompts.

## Metrics
- Per-part constraint rates: did each rubric part hold, and with what observed
  evidence (the `why`)?
- Scenario mean: average continuous score per scenario across trials.
- Overall mean + baseline delta: degradation detection (DEGRADED flag > 5pp).

## Rules
- Evals are run on demand (GPU), validated by eye/score-delta — not in CI.
- Never assert exact output; always score (per part + mean) over ≥3 trials.
- Never gate on a pass/fail threshold — report the continuous score so drift is
  visible.
- Add an eval when you change what the model is *expected* to do.
