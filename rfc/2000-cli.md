# 2000 — CLI

The command surface. **Status: RE-SCOPED (planned).** Currently `src/nimo.nim`
dispatches to per-tool binaries and exposes content-typed verbs (`chat`,
`story`, `pipeline`). The target surface is **goal-first** and **part-first**:
the user names the outcome ("create a story about…"), never the machinery, and
**every message part is invokable from the CLI**.

## The conceptual model

The chat interaction is *the CLI being invoked and its outputs chained*: each
message part (planner emission, generate, extract, summarize, validate, write,
lookup, report) is a CLI command. Running a command standalone is **ephemeral**
— it produces output but no session or workspace. A **session** is the
automation of these invocations with a history and a workspace; it materializes
only when you want context and persistence (`new <goal>`).

> **Conceptual only.** "Chat is the CLI chained" is a way to *think* about it —
> **in practice we never spawn a subprocess per part**, because each bootstrap
> loads the 2.2 GB model into VRAM. Instead:

- `new` / `open` / `continue` run as **one process: one `bootstrapSession`, one
  VRAM residency, one engine loop**. Message parts inside a session are called
  as **in-process functions on the already-loaded model** (`generateTurn`,
  `pipelineTool`, the pointed steps) — never spawned.
- Standalone part commands (`extract`, `generate`, …) accept a one-time
  bootstrap cost by design: "do one thing, quit." A conversation never pays it
  repeatedly.

The engine delegates to library *functions* on the bootstrapped session, not
subtask binaries (the current `harness main()` spawning `nimble run generate` via
`execCmd` is the anti-pattern this removes). A model-server daemon would only be
needed if we ever wanted subprocess-per-command; the running session already
*is* the resident model.

## The surface (target)

### Part commands — each message part, invokable (ephemeral by default)

```
nico planner "create a story about a lighthouse"   # show the plan the planner would create (compile only)
nico generate "<prompt>"                           # generate text (output skill)
nico extract --source <path> --for <what>          # pointed extract
nico summarize <input> --length brief              # pointed summarize
nico validate <file> [--min-words 500]             # pointed validate (gates)
nico write <path> <content>                        # pointed write
nico lookup "<query>"                              # memory lookup
nico report "<title>" --kind finished              # a report part
```

Flags like `--in <session>` attach a part to an existing session (recorded into
its history); without one, the call is ephemeral.

### Session verbs — drive the same parts with context

```
nico new "create a story about a lighthouse"    # open a session: compile goal -> plan, run the parts
nico open <id>                                   # attach to a session (stream / pause / resume)
nico continue <id>                               # resume where the plan stopped
nico list                                        # sessions: id, latest user message, status, updated
nico run <plan>                                  # execute an existing plan in a fresh session
```

Nothing here is a content type. `nico new story "..."` is **wrong** — "story"
is the orchestrator's decision from the goal. The old `chat`/`harness`/`story`
verbs collapse into `new`/`open` on a session; `plan` is spelled `planner`
when you want to preview what the planner would emit.

### Maintenance verbs

```
nico quantize <in.bin> <Q4_K> <out.bin>                       # quantize a model
nico bake [planner|output] <examples> <template>              # bake a skill state
nico unit                                                       # offline unit tests
nico model-eval                                                 # black-box model probes
```

## Why goal-first

- The user decides the **outcome**, not the **mechanism**. "Create a story
  about X" → orchestrator picks the story template; "remember this about X" →
  memory write; "what do I know about X" → memory lookup.
- The parts are still reachable directly (extract/summarize/validate/write/
  lookup/generate), so nothing is locked inside a session.
- Sessions become interchangeable: any goal runs in any session; you never
  choose a "kind" of session.

## Phase 6 mapping (plan/0015)

- `nico planner <goal>` — compile a goal into a plan artifact (**Ph 6**; the
  `plan` step of the turn).
- `nico run <plan> [--resume]` — execute with streaming (`nico continue`).
- `nico new <goal>` — the session entry point; wires `bootstrapSession` + the
  engine (Ph 0/3/6).
- Part commands (`generate`/`extract`/`summarize`/`validate`/`write`/`lookup`/
  `report`) map 1:1 to the engine's pointed steps (Ph 2/3) — standalone
  invocation is ephemeral; `--in <session>` records them.
- `nico story ...` (current) and `nico chat ...` / `nico harness ...` are
  **removed** from the surface (folded into `new`/`open`).

## Current commands (as coded, transitional)

```
nimo generate / quantize / harness / chat / bake / workspace / story / unit / eval
```

`workspace` management stays as a maintenance verb (`create`/`list`/`use`/
`status`/`remove`); sessions mount to a workspace via the `workspace` event.
