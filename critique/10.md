# Critique: Real-Human UX Simulation — Round 6 (the Unified Protocol REPL)

Round 6 implements the architectural direction requested: **a chat session is a
composition of small, deterministic operations; the REPL exposes those same
operations for a human to drive by hand.** RFC 2110 captures the design.

---

## The idea, restated

`nimo chat` is an *autonomous* driver of protocols (model picks). `nimo repl`
is the *human* driver of the exact same protocols:

- `send "Message"` == one harness turn (`runHarnessTurn`) — same as a chat turn.
- `planner "<goal>"` == `interpret(goal)` — deterministic, offline.
- `story chapter validate` == `validateChapter` — deterministic, offline.
- `ws` / `session` == the workspace/session primitives.
- `cuda status` == `gpuProbe`.

There is no second path for the model: both chat and repl get their model via
`bootstrapSession(cfg, cwd)` and run turns via `runHarnessTurn`. If you can
type it in the repl, the chat can do it — and vice versa.

## Implemented (Phase 1)

- `src/repl.nim` — `nimo repl`: quote-aware tokenizer, command dispatch,
  `help` (with per-command usage), and:
  - **Active session**: `send` / `steer` (run a turn), `queue` / `flush`
    (buffer N messages then run), explicit-verb discipline — a bare message is
    never inferred (Round 5 rule holds inside the REPL too).
  - **Offline, no GPU**: `ws new|switch|status|list`, `session new|status`,
    `planner "<goal>"`, `story chapter validate <file>`, `cuda status`,
    `state list`.
  - **Model-backed** (lazy, one bootstrap): `send/steer`, `story chapter
    write -p "…" [--skip-validate]`, `story wiki edit -p "…"`.
- `nimo repl` dispatch in `src/nimo.nim` (via the quote-preserving
  `joinQuoted`), help entries, `repl` task + bin in `nico.nimble`.
- `rfc/2110-repl.md` — the spec (status, invariant, grammar, seams).

## Verified like a human (tmux / stdin scripts)

```
$ nimo repl
nimo> ws new demo-ws                  → created + active
nimo> session new                     → active @ ~/.ws/demo-ws/session.jsonl
nimo> planner "create a story about a lighthouse"
    → plan steps (deterministic, offline)
nimo> story chapter validate README.md → words/paragraphs/repeating + quality
nimo> send "Say hello to the reader in one short line."
    → [backend] cuda … [model] loaded. … answer … done (2 steps)
nimo> quit
```

The online `send` loaded the real 2.2 GB model through `bootstrapSession` and
streamed a reply through `runHarnessTurn` — the *identical* seam the chat uses.
Offline, `send` runs against the stub generator and the whole REPL still works.

## Verdict

- The two surfaces are now provably the same machinery; the REPL is not a toy
  wrapper, it is the same engine with a human at the wheel.
- Offline testability: `nimo repl` works without GPU for planning/validation/
  workspace/session — a big win for deterministic testing.

## Known gaps (next rounds)

- `interrupt` (needs an async generation loop; currently a no-op).
- `state ingest` / `state load` (the bake/load primitives) — Phase 2.
- `story chapter write next --from <prev>` recap chaining.
- Chat-side `run_pipeline` still dispatches via its own tool handler; routing
  it through the SAME registry so the two surfaces share one code path is the
  RFC 2110 follow-up (RFC 2110 "Deliverables", second bullet).
- `planner --dry` is implied (planner never runs); a `--run` variant that then
  executes the plan is the natural next step.
